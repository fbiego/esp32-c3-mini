2026-07-12 — Why this directory exists, and how the pieces fit together
--------------------------------------------------------------------------
This is a *different* project from the earlier ESP32 watch work (~/OLEDS3Watch-joaquim,
based on joaquimorg/OLEDS3Watch). This one is built on fbiego's "Chronos" ecosystem,
found and already flashed to the board via the Claude app before Claude Code got
involved. Same class of hardware target (Waveshare ESP32-S3-Touch-AMOLED-2.06), but an
unrelated upstream codebase — do not mix the two up, and do not port code between them
without explicitly checking it makes sense for this firmware's architecture.

~/chronos-watch is a `git clone` of a fork (github.com/BigGremlin/esp32-c3-mini) of
https://github.com/fbiego/esp32-c3-mini — remotes: `origin` = the fork (push target),
`upstream` = fbiego's original (pull target for updates, and PR target).

This is THE FIRMWARE — the repo that actually builds and flashes to the watch. It's a
multi-board codebase: one platformio.ini with ~20 [env:...] sections, one per supported
board. Despite the repo being named after fbiego's original ESP32-C3 board, our board
(Waveshare ESP32-S3-Touch-AMOLED-2.06, 410x502 display) is a later-added target:
env:lolin_s3_2_06, board define ESPS3_2_06, extends the shared [esp32] section.
IMPORTANT: platformio.ini's `default_envs` is currently set to `elecrow_c3_1_28`, NOT
our board — any plain `pio run` without `-e lolin_s3_2_06` targets the wrong hardware.
Not yet fixed/changed, just noting it so it isn't a surprise later.

Related directories:
- ~/chronos-esp32 — fork+clone of fbiego/chronos-esp32 (the ChronosESP32 BLE library:
  notifications, weather, time sync, phone-battery relay via setBattery()). Same
  origin/upstream remote pattern as chronos-watch. NOT currently wired into the
  chronos-watch build — platformio.ini's `[esp32]` lib_deps pulls the PUBLISHED
  registry package `fbiego/ChronosESP32@1.9.0`, entirely independent of this local
  clone. If/when we need to patch the library itself, lib_deps will need to be
  repointed at the local fork (e.g. a path/symlink override) — not done yet.
- esp32-lvgl-watchface (bin2lvgl converter) and watch-face-wearfit (.bin dial pool) —
  not yet forked/cloned. Offline tooling for generating new watch faces; output gets
  dropped into chronos-watch/src/faces/ (existing faces there are named by pixel width,
  e.g. 174_410, 1167_410, gated by ENABLE_FACE_* macros in hal/esp32/app_hal.h). Only
  clone these when face-creation work actually starts.
- lewisxhe/XPowersLib — AXP2101 PMU reference library. Not yet forked/cloned; relevant
  only if/when real local battery-percentage hardware reading is added (see below —
  currently this board doesn't seem to have that wired up at all).

Local machine setup done this session: `gh` CLI installed (apt, already in Ubuntu 26.04
universe), authed as GitHub user BigGremlin via `gh auth login` (device-code flow, since
this machine is headless/SSH-accessed — browser auth happens on the connecting laptop,
not locally). User explicitly declined passwordless/NOPASSWD sudo when offered; ran the
one sudo install command themselves in a real terminal each time instead.

PR workflow (not yet exercised end-to-end): branch off `main` in the relevant fork,
commit, `git push -u origin <branch>`, then `gh pr create --repo fbiego/<repo>` to open
against upstream.

2026-07-12 (continued) — Battery-percentage: real AXP2101 read implemented, flashed, CONFIRMED working
------------------------------------------------------------------------------------------------------
Confirmed this board (Waveshare ESP32-S3-Touch-AMOLED-2.06, env:lolin_s3_2_06) is physically
the same PCB as the OLEDS3Watch-joaquim project's board: cross-checked hal/esp32/displays/pins.h
(LCD_CS=12, LCD_SCK=11, LCD_SD0-3=4/5/6/7, LCD_RST=8, TOUCH_RST=9, TOUCH_IRQ=38) against that
project's known-good esp32_s3_touch_amoled_2_06.h BSP header — every pin number matches exactly,
including the AXP2101 PMU's I2C bus (SDA=GPIO15, SCL=GPIO14 — same bus already used for touch in
this codebase, shared, not a separate bus) and address (0x34).

Implementation (all in hal/esp32/app_hal.cpp and platformio.ini, ESPS3_2_06-gated only, no other
board touched):
- platformio.ini, env:lolin_s3_2_06 lib_deps: added `lewisxhe/XPowersLib@0.3.3` (latest tagged
  release at the time; the library's git HEAD is ahead as 0.3.4-dev with a reorganized header
  layout — see gotcha below, don't assume HEAD's API/include-paths apply to the pinned version).
- app_hal.cpp: `#define XPOWERS_CHIP_AXP2101` + `#include <XPowersLib.h>` + `XPowersAXP2101 PMU;`
  global, declared right next to the existing `SensorPCF85063 rtc;` (same file, same pattern,
  same shared I2C bus).
- `PMU.init(Wire, TOUCH_SDA, TOUCH_SCL, AXP2101_SLAVE_ADDRESS)` called in hal_setup(), right after
  the existing `rtc.begin(Wire)` block (reuses the bus `tft.init()` already brought up via the
  touch driver — Wire.begin() with the same pins twice is safe/idempotent on ESP32 Arduino).
  Replaces the hardcoded `watch.setBattery(85)` with a real `PMU.getBatteryPercent()` read,
  passing `PMU.isCharging()` as the second arg (ChronosESP32's `setBattery(level, charging)`).
- hal_loop(): added a 30s-interval re-poll (static `millis()`-gated, ESPS3_2_06-only block) that
  re-reads and calls `watch.setBattery()` again, so the phone-visible battery % actually updates
  over time instead of being fixed at the boot-time value.
- Added a boot-time `Timber.i("AXP2101 battery: %d%%, charging: %d, vbus: %d", ...)` diagnostic
  log (kept permanently, not just for this session's verification — matches the existing
  Timber.e-on-failure convention for rtc.begin() right above it).

- First code attempt used `#include <XPowersAXP2101.hpp>` directly (matches the library's current

2026-07-12 (continued) — Real battery now wired into watch faces + Settings display, flashed
-------------------------------------------------------------------------------------------------
User feedback after the first battery fix: two of the enabled watch faces show a battery
indicator (`174_410`/`228_410`/`1167_410`/`2051_410`/`1041_410`/`2151_410` are the six faces
enabled for this board via ENABLE_FACE_*_410 in hal/esp32/app_hal.h; confirmed by viewing each
`watchface.png` preview that `1167_410` has a clear "battery %" bar/icon at top, and `2151_410`
— the one with the large orange moon the user likes — also has a battery-driven element), and
neither was showing anything real. Also: the "Battery" slider in Settings (`ui_batterySlider`,
`ui_batteryPanel`/`ui_batteryLabel`) is user-draggable, which the user correctly flagged as wrong
now that real battery hardware exists.

Root cause for the faces: found a single shared code path, `update_faces()` in app_hal.cpp,
computes one `battery` int for ALL watch faces via `watch.getPhoneBattery()` — i.e. every face's
battery indicator was actually showing the *connected phone's* battery (relayed over BLE), never
the watch's own. Confirmed via ChronosESP32 library header (`~/chronos-esp32/src/ChronosESP32.h`)
that `_batteryLevel` (the watch's own, set via `setBattery()`) has NO public getter — only
`_phoneBatteryLevel`/`getPhoneBattery()` is exposed — so faces structurally could not have shown
the real value even if someone tried, the API doesn't support reading it back.

Fix (all ESPS3_2_06-gated, no other board affected):
- Added a global `int watchBatteryPercent = 100;` next to the `PMU` object — our own tracked
  copy of the last good AXP2101 reading, updated by both the boot-time read and the 30s
  `hal_loop()` poll (added in the previous entry).
- `update_faces()`: `#if ESPS3_2_06` now sources `battery` from `watchBatteryPercent` instead of
  `watch.getPhoneBattery()`; `#else` unchanged for every other board (still phone battery, as
  originally designed there).
- Settings slider: `lv_obj_remove_flag(ui_batterySlider, LV_OBJ_FLAG_CLICKABLE)` right after
  `ui_init()` in hal_setup() (ESPS3_2_06-only) — stops it being draggable at all, without touching
  the auto-generated `src/ui/ui.c`. Both the boot-time read and the 30s poll now also call
  `lv_slider_set_value(ui_batterySlider, watchBatteryPercent, LV_ANIM_OFF)` and
  `lv_label_set_text_fmt(ui_batteryLabel, "Battery %d%%", watchBatteryPercent)` directly — bypasses
  needing to fire a synthetic LVGL VALUE_CHANGED event to get the "Battery NN%" label text to
  update (that logic normally only runs from `ui_event_batterySlider`'s VALUE_CHANGED handler,
  which itself only fires on user drag or an explicit `lv_event_send()`).
- `onBatteryChange()`/`ui_event_batterySlider` (the old drag-to-fake-a-level handler) intentionally
  left in place, untouched — now simply unreachable by touch since the slider isn't clickable, no
  need to delete it (and it's still the correct/only behaviour on every other board, which don't
  have a real PMU and still rely on this control to simulate a level for `getPhoneBattery()`-driven
  face testing).

Built clean, flashed, reconfirmed boot log still shows `AXP2101 battery: 100%, charging: 0,
vbus: 1`. **Not yet visually confirmed on-device** that the moon face (2151_410), 1167_410, and
the Settings screen actually render 100% correctly and that the slider truly can't be dragged —
user is doing their own significant testing pass before any of this gets committed. (Update
2026-07-13: 1167_410 specifically WAS checked, and did not render correctly — see below. The
other four enabled faces are still unconfirmed.) Included in the same `00a1022` commit as the
previous entry.

**Open question for later, not addressed:** the four other enabled faces (`174_410`, `228_410`,
`2051_410`, `1041_410`) were not individually checked for whether they also render a battery
element — the `update_faces()` fix applies uniformly to all of them since it's one shared
function, so they should also now show the real value if they bind to it at all, but their
`watchface.png` previews weren't inspected for a battery indicator specifically (only 1167_410
and 2151_410 were, per the user's report of "along with one of the other watch faces").


2026-07-12 — "Funny state" after reboot: screen goes dark, unresponsive to touch — RESOLVED, nvs erased
---------------------------------------------------------------------------------------------------------
Symptom: watch showed a boot splash, then went dark and stayed dark; appeared totally
unresponsive to touch. A soft reset (DTR/RTS pulse over the native USB-Serial-JTAG
link, same mechanism esptool/idf-monitor use — /dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_80:B5:4E:F3:30:F4-if00)
produced a clean boot log (`Setup done`, `v6.3 [fbiego]`, ESP32-S3, MAC 80:b5:4e:f3:30:f5)
but the dark-screen/no-touch-response symptom persisted. A full physical battery
disconnect (~10 min, the known fix for this hardware family's occasional stuck-PMIC
state — see the OLEDS3Watch project's equivalent note) made no difference either.

Root cause, found by reading source: brightness is persisted via the ESP32
`Preferences` library (`prefs.begin("my-app")`, app_hal.cpp:1837) into the `nvs`
partition (partitions_16M.csv: offset 0x9000, size 0x5000 / 20KB) — separate from the
firmware itself (`app0`) and watch-face storage (`ffat`). At boot it loads
`prefs.getInt("brightness", 100)`. Critically, the main loop's screen-wake path
(app_hal.cpp ~2330) re-applies that *same stored value* every tick whenever the screen
is "on" (`screenBrightness(lv_slider_get_value(ui_brightnessSlider))`), and the touch
handler (`my_touchpad_read`, app_hal.cpp:271-284) does correctly call `screen_on()` on
a real touch — so the "wake" logic was working, but brightness was being force-set back
to whatever was last saved (near 0) every time. Matches the user's own account: the
last action before the funny state was dragging the brightness slider down.

Fix applied: erased just the 20KB `nvs` partition via `esptool erase-region 0x9000
0x5000` — resets brightness/timeout/touch-calibration/etc. back to firmware defaults,
does not touch firmware (`app0`) or watch-face data (`ffat`). Confirmed working
on-device afterward (screen now shows content on boot, user confirmed).

Tooling note for next time: the Debian/Ubuntu apt package `esptool` (4.7.0+dfsg) is
missing its bundled stub-flasher binaries (dfsg repackaging strips precompiled blobs),
so `erase_region`/most flash operations fail even with `--no-stub` (ROM bootloader
alone doesn't support erase_region). Fix: installed real esptool from PyPI into
`~/.local` via `pip3 install --user --break-system-packages --ignore-installed
--force-reinstall esptool` (got 5.3.1). Use `~/.local/bin/esptool` (note: no `.py`
suffix needed/preferred; `esptool.py` invocation form is deprecated) for any future
flash-level operations on this board, not the apt one.

Possible side effect not yet confirmed either way: erasing `nvs` may also have cleared
BLE pairing/bonding state (same partition, no dedicated bonding partition in
partitions_16M.csv) — may need to re-pair with the Chronos phone app. Not confirmed
broken or working, just flagging it as untested.


2026-07-13 — 1167_410 face: battery bar wraps to empty at full charge, percentage missing its ones digit — FIXED, flashed, confirmed
------------------------------------------------------------------------------------------------------------------------------------
User-reported symptom, on the real device with the now-real AXP2101 reading in place (previous
entry): the 1167_410 face's battery bar icon looked fine while charging but dropped to empty right
at 100%, and the percentage number was missing its last digit (40% displayed as "4").

Root cause, in `update_status_1167_410()` (src/faces/1167_410/1167_410.c):
- Bar: `face_1167_410_2_112000` (11-frame icon) was indexed with
  `(battery / (100 / 11)) % 11`. Integer division: `100/11` truncates to `9`. At `battery=100`,
  `100/9=11`, `11%11=0` — wraps back to the empty frame exactly at full charge.
- Digits: three image slots existed (`face_1167_410_3_171192` at x=189 showing `battery/10`,
  `face_1167_410_4_171192` at x=172 showing `battery/100` correctly hidden except at exactly 100%,
  `face_1167_410_5_171192` at x=155 showing `battery/1000` — always zero for a 0-100 value, and
  *not* hidden). No slot ever computed `battery%1` (the true ones digit), so the tens digit at
  x=189 was the only thing that ever visibly changed — hence "4" instead of "40".

Fix (src/faces/1167_410/1167_410.c + .h, this face only — bug pattern likely exists in sibling
faces generated by the same bin2lvgl pipeline, e.g. plain `1167`, but only 1167_410 was touched
since it's the only one of that family enabled/tested on this board):
- Bar index changed to `(battery / 10) % 11` — maps 0-100 onto 0-10 directly, no wraparound
  possible for any value in range.
- Added a new digit image object `face_1167_410_47_171192` (positioned x=206, 17px right of the
  tens digit at x=189 — matches the existing 17px digit pitch), driven by `(battery / 1) % 10`.
- Hid the always-zero thousands-digit slot (`face_1167_410_5_171192`) permanently at init — it's
  meaningless for a 0-100 value and was left visibly showing a stray "0".
- First flash attempt showed the new ones-digit overlapping the '%' glyph badly (glyph is 15px
  wide, new digit slot only had ~4px clearance before the '%' at x=210). Moved the '%'
  (`face_1167_410_6_175276`) from x=210 to x=227 to clear it.

Verified: `pio run -e lolin_s3_2_06` builds clean, flashed via
`pio run -e lolin_s3_2_06 -t upload --upload-port /dev/ttyACM0`, user confirmed on-device the bar
holds full at 100% and the percentage now reads correctly as two digits with the '%' clear of the
new digit.

Committed as `e7ac3b1` on branch `fix/1167-410-battery-digit` (see branch-strategy entry below).


2026-07-13 — Investigated: touch-to-wake battery drain, and AXP2101/RTC power-off behaviour (no code change, findings only)
------------------------------------------------------------------------------------------------------------------------------
User observation: "touch to wake" seems to drain the battery heavily, and when the battery goes
fully flat the watch appears to power off but the RTC keeps time regardless — asked how the
firmware decides to power off, and whether it's safe for the RTC to be drawing off a flat battery.

Findings, from reading hal/esp32/app_hal.cpp (no fix attempted, this was pure investigation):
- There is no real sleep state anywhere in this firmware — grepped for `esp_sleep`,
  `esp_light_sleep_start`, `esp_deep_sleep`, `gpio_wakeup` across `src/` and `hal/`: zero hits.
  "Screen off" (the `screenTimer` timeout, ~line 2387, "Screen timeout" log) only calls
  `screenBrightness(0)` — for this board that's `tft.setBrightness(0)`, a backlight PWM call. It
  does not sleep the display panel or the ESP32.
- `hal_loop()` (line ~2201) runs unconditionally every ~5ms regardless of screen state:
  `lv_timer_handler()` (full LVGL redraw/animation tick — the seconds hand keeps animating with
  the backlight off), `watch.loop()` (ChronosESP32 BLE + touch-input processing), plus a 30s
  AXP2101 battery poll over I2C (added in the 2026-07-12 battery-reading work above). So the CPU,
  touch controller, LVGL, and BLE stack are at full active-mode current draw the entire time the
  screen is dark — "touch to wake" is not waking from sleep, there's no sleep to wake from. This is
  the actual drain source, not the touch polling itself.
- Grepped every `PMU.` call site in the codebase: only `.init()`, `.getBatteryPercent()`,
  `.isCharging()`, `.isVbusIn()` exist. No `setSysPowerDownVoltage`, no low-battery shutdown IRQ
  config, nothing — the firmware never tells the AXP2101 when to cut power. The power-off observed
  at empty battery is the AXP2101's own factory-default hardware over-discharge protection, not a
  firmware decision.
- RTC-survives-flat-battery: not verifiable from this repo (board wiring/schematic, not firmware),
  but the PCF85063 is a separate low-power timekeeping chip and boards built around it near-
  universally give it its own small backup source (backup cap or coin cell) isolated from the main
  battery rail, specifically so it survives the PMIC cutting the main rail — standard, expected,
  safe design. Would need the Waveshare board schematic to confirm definitively for this specific
  unit; not available in this repo.

Not started: an actual real-sleep implementation (light sleep + touch-controller IRQ as wake
source) would fix the drain, but is a real feature addition, not attempted this session.

  `uv python install 3.11`), then `uv venv --python 3.11 .venv` + `uv pip install Pillow` inside

- **`resizer.pyc` turned out to be a dead end**: despite the README documenting
  `py resizer.pyc watchface.bin 240 360` (from-size, to-size args) and the tool printing a
  "AxA >> BxB" banner reflecting whatever's typed, the actual resize target is hardcoded — same
  output file (byte-identical size) regardless of what width arguments were passed. Confirmed via
  `strings resizer.pyc`: the banner text is a literal constant, not built from argv. Do not trust
  this tool's documented interface; if a real fix is ever wanted, decompiling the bytecode (no
  `.py` source ships in the repo) would be the only path, or just keep using the approach below.

Actual approach used (bypasses resizer.pyc and the proprietary `.bin` dial format entirely):
run `bin2lvgl.jar` once on the 240x240 source `.bin` to confirm/inspect structure, but the real
source of truth was chronos-watch's own already-converted `src/faces/75_2/assets/*.c` — decode
those LVGL C image arrays directly back to pixel data, scale with Pillow, re-encode to the same
LVGL C format. New helper module: `tools/facegen/lvgl_img.py` (decode/encode/format functions),
driver script `tools/facegen/gen_75_2_410.py` (scales 75_2 → 75_2_410 specifically; adjust the
`SRC_DIR`/`OLD`/`NEW`/target-width constants at the top to reuse for a different source face or
target resolution).

**Two real format gotchas hit and fixed, worth knowing before touching these asset files again:**
1. `.header.always_zero = 0,` vs `.header.magic = LV_IMAGE_HEADER_MAGIC,` — bin2lvgl emits
   different header-field names across files/versions (even inconsistently within the same
   `75_2` face — the alpha-less background asset used `magic`, the alpha-bearing hand/text assets
   used `always_zero`). This project's pinned LVGL (9.3.0) only has `magic` on
   `lv_image_header_t` — `always_zero` doesn't exist and fails to compile. This never surfaced
   before because `75_2` was never enabled on any board that actually got built (its
   `ENABLE_FACE_75_2` guard was never defined for `ESPS3_2_06`) — first time enabling it here is
   what exposed the latent bug. Fix: always emit `.header.magic = LV_IMAGE_HEADER_MAGIC,`.
2. **Pixel data layout is planar, not interleaved.** For `LV_COLOR_FORMAT_NATIVE_WITH_ALPHA`
   (RGB565 + alpha), the byte array is NOT `[R,G,alpha, R,G,alpha, ...]` per pixel — it's all
   `w*h*2` RGB565 color bytes first, THEN all `w*h` alpha bytes after (confirmed by exact byte
   count: a 10x66 image is 1980 bytes = 660*2 (color) + 660*1 (alpha), not divisible cleanly any
   other sensible way). Decoding as interleaved-per-pixel produces a subtly-broken image where
   most fully-opaque regions look fine (background, solid fills) but anything with real alpha
   transitions — edges, thin strokes, text — comes out as scattered colour speckling, because
   each "pixel" read is actually built from bytes belonging to 1-2 *different* real pixels plus a
   stray alpha byte. This is exactly what the user saw on the first flash (hands + weekday text
   speckled, solid background fine) and initially misdiagnosed as a resize-filter ringing problem
   (tried LANCZOS→BICUBIC, tried adding alpha premultiplication — neither helped, because neither
   was the actual bug). Confirmed by direct pixel inspection of a decoded-but-unscaled hand image
   at 8x nearest-neighbour zoom — the speckling was present before any resize step ran at all,
   which is what finally pointed at the decode step itself rather than the resize.

Face itself: root object's black background is used for letterboxing — since 75_2 is a 240x240
square design and this screen is 410x494 (not square), the scaled 410x410 result is vertically
centered with a 42px black margin top and bottom (`Y_OFFSET = (494 - 410) / 2` in the script)
rather than distorting it into an oval to fill the full height. All positions and hand pivot
points scaled by the same 410/240 factor as the images themselves, so rotation stays correctly
centered.

Wired up ESPS3_2_06-only: `ENABLE_FACE_75_2_410` added to `hal/esp32/app_hal.h`'s `ESPS3_2_06`
block, `init_face_75_2_410`/`update_check_75_2_410` added to `ui_watchfaces_init()`/
`ui_update_watchfaces()` in `src/ui/ui.c`. New face lives at `src/faces/75_2_410/`. Builds clean,
flashed, user confirmed hand rotation, letterboxing, and (after the planar-decode fix) the
speckling are all good.

**Deliberately NOT going to `fix/*` / upstream** — this is this-repo-specific tooling output

2026-07-20 (cont. 4) — Extreme Power Save: investigation + plan, steps 1-2 done
------------------------------------------------------------------------------------------------
New feature request: port as much of OLEDS3Watch-joaquim's power-management work as makes sense,
gated entirely behind a new "Extreme Power Save" Settings switch - when on and on battery, sleep
as deep as possible (CPU, touch, BLE all off); when off, current behaviour unchanged. Before
touching code, did two rounds of investigation per explicit user request.

**Button investigation.** This board (`ESPS3_2_06`) has two physical buttons: GPIO0 ("BOOT") and
a bare hardware EN/CHIP_PU reset (never software-visible on any ESP32 board, nothing to reference
in firmware, identical behaviour regardless of project). `BUTTON_HOME` (GPIO0) is an established
pattern already used by `ELECROW_S3`/`VIEWE_*`/`ESP32_CYD` in `pins.h`, and confirmed as real,
working hardware on this exact board via `OLEDS3Watch-joaquim` (same physical board, GPIO0 polled
every 50ms for its button-sleep feature) - but `ESPS3_2_06` never had `BUTTON_HOME` defined, so
chronos-watch's existing `Button2`/`btn_home_handler` code (single/double/triple/long-click, all
already written) was simply dead for our board. Zero risk of clobbering anything on our board.

**Display-pipeline risk investigation**, since OLEDS3Watch-joaquim's own attempt at real light
sleep (`8a4fa1b`/`81340bd`) caused a confirmed, severe display-banding regression there and was
fully reverted (`58708c9`) - root cause never fixed, just avoided. Checked joaquim's *current*
state precisely rather than trusting old notes: `CONFIG_FREERTOS_USE_TICKLESS_IDLE is not set`,
`display_manager_pm_early_init()` defined but never called - light sleep is genuinely inert there
today. Joaquim's own root cause was `trans_queue_depth=32` (deep async SPI transaction queue)
getting transactions dropped/reordered under load. Chronos-watch's own display stack was checked
directly rather than assumed safe-or-not: same general chunked-partial-buffer LVGL pattern (40-line
buffer, even shorter than joaquim's 100), but a **completely different driver** - `Arduino_GFX`
(not ESP-IDF's `esp_lcd` BSP driver), `Arduino_ESP32QSPI` bus with `.queue_size = 1` (checked the
actual library source) - i.e. transactions are effectively blocking/synchronous, one at a time.
This structurally rules out joaquim's specific reorder/drop failure mode (there's nothing to
reorder with a depth-1 queue), though a lesser sleep-induced-delay-between-chunks risk could still
exist and needs real on-device testing, not just this static analysis.

**Also confirmed**: chronos-watch has zero WiFi usage anywhere (nothing to turn off there), and
ChronosESP32 already exposes a clean `watch.begin()`/`watch.stop(bool clearAll)`/`watch.isRunning()`
API for BLE - `stop(true)` fully deinits NimBLE, no internal hacking needed. `TouchDrvFT6X36` (our
touch driver) already has `sleep()`/`wakeup()` methods (wakeup calls `reset()` internally) - cleaner
than joaquim's manual GPIO-reset-hold. User confirmed: BLE should be **fully stopped** (not just
touch/CPU sleeping) while asleep on battery - it's a real power draw and phone reconnect-on-wake is
an acceptable tradeoff.

**Agreed plan, staged, one tested/flashed piece at a time** (matching this project's established
pattern): (1) enable GPIO0 button, isolated test. (2) Add the Settings switch, persisted, no
behaviour yet. (3) Charge-aware screen timeout (stay on indefinitely on `PMU.isVbusIn()`, button
forces off regardless of power state) gated by the switch. (4) Touch sleep/wake tied to
screen-off-while-on-battery + switch. (5) BLE stop/begin tied to the same condition - flagged to
verify on-device whether the phone reconnects cleanly after a stop/begin cycle. (6) CPU light sleep
last, its own isolated experiment, since it's the one piece with no working precedent to lean on.

2026-07-20 (cont. 5) — Step 6 (CPU light sleep) ATTEMPTED, ABANDONED - real USB-disruption bug found
------------------------------------------------------------------------------------------------
Investigated and implemented, then fully reverted (never committed - `git checkout` cleanly
restored `hal/esp32/app_hal.cpp` to the step-5 state, `0b92022`). Recording the full investigation
here so nobody re-attempts this blind later - the finding is real and toolchain-specific, not a
one-off fluke.

**First: confirmed the "automatic" path is a dead end, then found a viable-looking alternative.**
Checked the actual precompiled sdkconfig for this exact board/toolchain
(`~/.platformio/packages/framework-arduinoespressif32/tools/sdk/esp32s3/qio_opi/include/sdkconfig.h`,
`qio_opi` being `lolin_s3_pro`'s `memory_type` per its board JSON) - neither
`CONFIG_FREERTOS_USE_TICKLESS_IDLE` nor `CONFIG_PM_ENABLE` are defined anywhere in it. So the
automatic/tickless-idle approach joaquim tried isn't just risky here, it's not even compiled in.
But a manual/explicit alternative looked viable: `esp_light_sleep_start()` +
`esp_sleep_enable_ext0_wakeup()` don't depend on tickless idle at all. **Verified this empirically,
not by assumption** - added a temporary probe function (never called, guarded by a
compiler-unprovable `volatile bool` so the linker couldn't dead-strip it), built, confirmed it
linked cleanly (~8.4KB of real object code pulled in), then removed the probe with zero trace
before writing the real implementation.

**Implementation**: new `deep_idle_loop()`, entered from the top of `hal_loop()` only once
`touchAsleep && bleAsleep` are both already true (steps 4/5's own gate) - deliberately *not* relying
on automatic idle-triggered sleep, entering a dedicated loop only once nothing is being
rendered/transmitted, specifically to avoid joaquim's mid-flush-interruption failure mode. Loop:
`esp_sleep_enable_ext0_wakeup(GPIO_NUM_0, 0)` (button) + a 2s periodic timer re-check, calling
`esp_light_sleep_start()` repeatedly; breaks out on an `ESP_SLEEP_WAKEUP_EXT0` cause and lets the
normal `hal_loop()`/`btn_home.loop()` flow take over from there (deliberately does *not* call
`screen_on()` itself, so Button2's own click-type classification stays undisturbed).

**Bug 1, found and fixed**: button couldn't wake it at all. Read `sleep_modes.c` directly (this
machine has a local `~/esp-idf` checkout) - `esp_sleep_enable_ext0_wakeup()` switches the pin to
RTC-IO function during sleep prep but never touches its pull resistors; Button2's digital-domain
`INPUT_PULLUP` doesn't apply once the pin is in RTC function, so it floats during actual sleep.
Fixed with `rtc_gpio_pullup_en()`/`rtc_gpio_pulldown_dis()` before `esp_sleep_enable_ext0_wakeup()`,
plus `rtc_gpio_deinit()` after the loop exits to restore plain digital mode for Button2's
subsequent polling. **Built, flashed, tested - still didn't wake from battery.**

**Bug 2, found via a live-serial diagnostic build, NOT fixed - real toolchain limitation.** Couldn't
watch the actual on-battery failure live (being connected to this machine's USB *is* VBUS power,
which prevents the sleep path from ever engaging at all - a real methodological catch-22). Worked
around it with a temporary `on_battery()` override (hardcoded `return true`, replacing all four
`PMU.isVbusIn()` call sites for this feature) so the exact same code path could run while still
connected for live serial visibility, plus added verbose per-iteration logging
(`esp_light_sleep_start()`'s return code, wakeup cause, live `digitalRead(0)`). This revealed the
real picture:
- `esp_light_sleep_start()` itself works fine - returns cleanly every ~2s, `rc=0`, no hang. This
  ruled out the "PM component not initialized, sleep call hangs" theory outright.
- Every single wake reported `cause=4` (`ESP_SLEEP_WAKEUP_TIMER`) - never `cause=2` (`EXT0`), i.e.
  button wakeup genuinely never registers no matter what.
- **While watching, the device vanished from the USB bus entirely** (`lsusb` showed nothing
  matching Espressif's vendor ID, not just a renamed serial port) - even though it was plugged in
  continuously the whole time. It did not come back on its own; needed a physical unplug/replug to
  recover, every single time, across several repeated occurrences while trying to reflash the
  revert afterward.

**Conclusion: `esp_light_sleep_start()` disrupts USB connectivity on this exact board/toolchain
combination badly enough to need a physical replug to recover, and separately never delivers a
genuine EXT0 wakeup.** This is very plausibly *why* Espressif shipped this Arduino core variant
with `CONFIG_PM_ENABLE`/tickless-idle disabled in the first place - not an oversight, a deliberate
choice given unresolved peripheral interactions like this. Matches what the user saw independently
on real battery testing (stuck asleep, only a fresh USB connection - not the button - brought it
back), which in hindsight was the same USB-disruption symptom, not a hang inside the sleep call.

**Fully reverted, nothing committed.** `git checkout -- hal/esp32/app_hal.cpp` cleanly restored the
step-5 state (`0b92022`) - the diagnostic/probe code left zero trace. Had to fight through several
rounds of the device dropping off USB mid-reflash (same underlying disruption, lingering from the
firmware that was still running during the revert-and-reflash attempts) before successfully getting
the known-good step-5 build back onto the device and confirming a clean boot + normal heap
(~19KB free, matching pre-step-6 readings, vs ~14KB while the sleep code was resident).

**Extreme Power Save feature considered DONE as of here, steps 1-5 only.** Screen dimming, touch
sleep, and BLE stop already cover the bulk of the real power draw; CPU stays awake, which is a
real but comparatively small remaining gap. Step 6 is not being re-attempted without a materially
different approach (e.g. a from-source Arduino-ESP32 core build with PM properly enabled and
tested - a much larger undertaking, not a simple project-level change) - don't re-attempt the
`esp_light_sleep_start()` approach on this toolchain again without reading this entry first.


2026-07-20 (cont. 6) — Step 6 RETRIED with ext1 (user supplied external research), same conclusion
------------------------------------------------------------------------------------------------
User dropped a research document into the scratchpad
(`ESP32-S3_AMOLED_2.06_LightSleep_DeepDive.md`) after the cont. 5 abandonment, citing a real,

pin through sleep), which ext0 never did - added `rtc_gpio_hold_dis()` after wake, on top of the
existing `rtc_gpio_pullup_en()`/`pulldown_dis()`/`rtc_gpio_deinit()` from the ext0 attempt.

target condition) removes exactly what made the diagnostic test pass. This is not something fixable

2026-07-20/21 (cont. 7) — Step 6 retry #3 (timer-poll, no GPIO wake source) - WORKING, user soak-testing
------------------------------------------------------------------------------------------------
User's own idea, prompted by re-examining the cont. 5/6 logs: `esp_light_sleep_start()`'s **timer**
wake had been 100% reliable in *every* test across both prior attempts (`rc=0`, clean, every single
cycle, no exceptions - only the RTC-GPIO wake trigger itself was ever unreliable). So instead of
depending on ext0/ext1 at all, this version doesn't configure a GPIO wake source - it just polls
GPIO0 with a plain `digitalRead()` every time the periodic timer wakes it (200ms interval), and
treats a LOW reading as "wake now". GPIO0 never switches to RTC-IO function this way - it stays in
Button2's own digital mode the whole time - which sidesteps the entire class of problem cont. 5/6
hit, rather than working around it. Tradeoff: button response is bounded by the poll interval
(≤200ms) instead of instant, judged an acceptable cost given two failed attempts at instant wake.

**Confirmed working on real battery on the first genuine test** - the first time any wake mechanism
in this whole step-6 saga has worked off USB power. Then three more real bugs surfaced through
actual use, each found and fixed same-session:

1. **Wake press got misclassified as a long-click, jumping into the face picker instead of just
   waking.** Root cause: the original design deliberately let Button2 see and classify the
   wake-triggering press itself (see cont. 5's original comment, now stale). Button2 hadn't polled
   in seconds (asleep the whole time) - handing it a still-down button as its first fresh reading
   let it measure the hold from an arbitrary starting point. **Fix**: consume the wake press
   entirely inside `deep_idle_loop()` - call `screen_on()` directly the moment a LOW read is seen,
   then busy-wait for the physical release before returning control to the normal loop, so
   Button2's first post-wake poll always sees a clean "not pressed" state and only a genuinely new
   press after this one ever gets classified as a click.

2. **A held-a-bit-longer wake press (past a first-pass 2s release-wait cap) still flashed the
   screen on then immediately off.** The release-wait loop's timeout was too short - a plain
   "hold the button a little longer than a quick tap" (very normal human behaviour, especially
   given the up-to-200ms response lag makes people unsure whether their press registered) exceeded
   2s, handed the still-down button to Button2 after all, which read it as a fresh press on an
   already-awake home screen and fired the existing press-to-turn-off toggle - instantly undoing
   the `screen_on()` from fix #1. **Fix**: extended the release-wait cap to 15s (only meant as a
   safety net against a genuinely stuck/shorted pin, not a real expected wait - any realistic human
   hold is comfortably under that).

3. **With fix #2 in place, the screen wouldn't visibly light up at all until the button was
   released** ("won't start up until I take my finger off the button" - but a snappy tap still
   worked instantly). Root cause: `screen_on()` only sets `screenTimer`'s flag/timestamp - the code
   that actually restores the physical backlight (`screenBrightness()`) lives further down in the
   *same* `hal_loop()` call, which is never reached until `deep_idle_loop()` returns - and fix #2's
   release-wait loop blocks synchronously right there, so nothing calls `screenBrightness()` until
   release. **Fix**: call `screenBrightness(lv_slider_get_value(ui_brightnessSlider))` directly,
   immediately after `screen_on()`, so the physical backlight comes on right away regardless of how
   long the subsequent release-wait blocks for. Needed a forward declaration
   (`void screenBrightness(uint8_t value);` near the other forward decls) since the real definition
   sits much later in the file than `deep_idle_loop()`.

**User confirmed all three fixes working together on-device**: quick tap wakes instantly, a longer
held press now lights the screen immediately too and stays on properly after release, in both
cases resuming to the watch face rather than the face picker.

day before finalizing - this note exists so a fresh session picks up the right state rather than

2026-07-30 (cont.) - wake-from-sleep-on-battery regression traced to internal-heap exhaustion,
classic_410 cogs iterated heavily (window narrow/taper false start, teeth taper, colours,
date window), 2151_410 month/day swap
------------------------------------------------------------------------------------------------
**Bug report: watch stopped waking from sleep on battery**, reported right after the cogs commit
above. Confirmed the wake-path code itself (`deep_idle_loop()`/`on_battery()`, step 6) hadn't
changed since its soak-tested, working commit (`9121f7c`) - so not a regression in that code
directly. Root cause found via a live serial boot capture (not just static analysis): **internal
heap at 98.66% used, `E BLE_INIT: Malloc failed` logged at every boot.** `include/lv_conf.h:47`
hardcodes `LV_USE_STDLIB_MALLOC = LV_STDLIB_CLIB`, which overrides the `LV_MEM_SIZE`/`LV_MEM_CUSTOM`
build flags in `platformio.ini` entirely (those only apply under `LV_STDLIB_BUILTIN`) - so
`lv_malloc()` is plain `malloc()` on the same general heap BLE/WiFi need. ESP-IDF's allocator only
spills a single allocation into the 8MB PSRAM once it exceeds a size threshold; anything smaller
always comes from the tiny (~183KB) internal-only heap regardless of how many such small
allocations pile up. classic_410's ~36 gear/tooth/hub `lv_obj_t` widgets (all well under that
threshold) had been landing there permanently since boot, on top of everything else already
enabled - tipping internal heap usage over the edge to where BLE's own re-init (`watch.begin()`,
called from `screen_on()` on every wake) could no longer allocate.

**Fix**: `heap_caps_malloc_extmem_enable(128)` added at the top of `hal_setup()`
(`hal/esp32/app_hal.cpp`, `#if ESPS3_2_06`-gated), lowering the spill threshold so small
allocations also go to PSRAM. Confirmed via two fresh serial boot captures: free internal heap
2504 -> 12256 bytes, `BLE_INIT: Malloc failed` gone both times. **Not yet confirmed by an actual
on-device battery wake test** - the boot-time BLE fix is verified, but nobody has yet pressed the
button on unplugged hardware to confirm wake itself is restored. Ask before assuming it's fully

2026-07-31 - classic_410 cogs rebuilt as raster images (chrome art masked to a
physically-correct meshing silhouette), replacing the widget-tree teeth entirely
------------------------------------------------------------------------------------------------
User's verdict on the teeth-taper widget version (photographed on real hardware): "look like

only fill an optionally-rounded rectangle via styling, there's no polygon/trapezoid primitive, so
the 2-rect stack was a hack around that limit, not a real tapered shape), and **what the cogs
actually cost on the ESP32** (answer, reasoned from config since `LV_USE_PERF_MONITOR` was never
enabled: display is `LV_DISPLAY_RENDER_MODE_PARTIAL` and the mech window is only 128x64px, so the
20Hz `gear_timer_cb` redraw is bounded to that tiny dirty rect regardless of gear complexity -
unlikely to be "overloading" the chip, but the ~60-object teeth-taper version doubled the CPU cost
of that redraw for zero visual gain given the "looks like shit" verdict).

That cost/quality analysis led to a recommendation, accepted by the user: stop layering more
widget hacks on a fundamentally rectangle-limited primitive, and bake each gear as one raster
image instead (fewer objects - 3 rotated image blits total instead of ~69 separate widgets - and
arbitrary shapes/anti-aliasing become trivial). Iterated in stages, each checked visually before
moving on (screenshots sent via SendUserFile, not flashed until the shape itself was right):

1. **Procedural placeholder** (`tools/facegen/gen_cogs_classic_410.py`): flat-grey gears with a

   only the magnitudes were wrong). `gear_timer_cb` now accumulates in float degrees (not the
   integer-degree accumulator the old code used) so the non-integer per-tick deltas (e.g.
   51/14 = 3.643 deg) don't compound rounding error - only the final `lv_image_set_rotation` call
   rounds, the running total stays exact.

   teeth tips turned out to reach almost exactly to the 1024-canvas edge (outer radius ~504-512px
   out of 512). `render_gear()` gained a `scale` parameter (zooms pitch_r/module/pad/spool

**Exact-tangent mesh placement**: replaced the eyeballed `ga_x/gb_x/gc_x` with real geometry - two
gears mesh exactly when centre-to-centre distance equals the sum of their pitch radii. Chain
topology only (a-b mesh, b-c mesh, a and c don't touch) - three *mutually* meshing external gears
in a closed triangle is a mechanically impossible odd cycle (same parity argument as a triangle not
being 2-colourable), so this was never going to be a triangle regardless. Added `GEAR_GROUP_SCALE`

narrow angles read "too close", 14 still narrow read "too far", 18 at wider angles read "still a
tooth-length too far", 8 read closer but wanted "a tiny bit tighter", landed on 5).

**The mesh-phase puzzle - math and hardware disagreed, hardware won.** Independent of spacing,
gear_b's own baked tooth phase is arbitrary (whatever the hi-res source art happened to render) and
unrelated to gear_a/c's - two gears meshing needs a *valley*, not a tooth, facing the contact point.
Derived initial rotation offsets per gear from first principles (tooth 0 sits at clock-angle 0 in
the baked art; a valley needs `contact_bearing - halfTooth` rotation) and snapped the b-c arm angle
so `(bc_angle - ba_angle)` lands on an exact multiple of gear_b's own tooth pitch - meaning gear_b's
one fixed tooth pattern should, in principle, face a valley toward *both* neighbours from a single
rotation value. Verified this numerically (not just visually) two different ways - a local
rotate-and-composite simulation, and a direct "nearest-tooth-offset" calculation - both agreed the
derived phase gives the maximum possible valley clearance (not a tooth collision) at all four
contact checks. **User reported the opposite from the real device, twice, independently, with a
specific fix ("rotate the middle cog by half the angle between teeth")** - tried that fix in
simulation first and it mathematically produces exact tooth-on-tooth collision by the same model,
the polar opposite of what should help. Never found the actual discrepancy between the verified
model and the hardware (checked the compiled macro expansion matched the Python model, checked the
object file was newer than the source so it wasn't a stale build, checked the baked art's tooth-0
position empirically against the "clock-angle 0" assumption - all consistent with the model being
right). Applied the user's confirmed-on-hardware fix anyway (`GEAR_B_PHASE_DEG` simplifies to plain

flagging the unresolved contradiction for whoever's next in this code. **Lesson: trust the person
looking at the physical device over an internally-consistent theoretical model that can't be
directly observed - two independent, specific, repeated reports beat re-deriving the same proof a
third time.**

2026-08-25 - Button unresponsive after ~10s while awake - FIXED, flashed, confirmed, committed
------------------------------------------------------------------------------------------------
User-reported symptom: screen stays lit, but the home button stops responding roughly 10-15s
after wake/interaction, recovering after about a minute; single presses were also occasionally
misread as long-presses (jumping into the watchface picker unprompted).

Live serial capture (pyserial, `/dev/serial/by-id/usb-Espressif_USB_JTAG_serial_debug_unit_*`,
115200) showed continuous `Wire.cpp:513 i2cRead Error -1` firing roughly once per second, present
the entire capture regardless of whether the button was currently responsive - ruling out the
first theory (AXP2101 stuck-register state, normally cleared by a physical battery disconnect per
earlier entries in this file). A battery pull was tried anyway as a sanity check; errors resumed
immediately on reconnect, confirming this run was a different mechanism than the earlier
stuck-register cases, or that the disconnect alone isn't sufficient this time.

Root cause found by reading, not just logging: `staying_on_for_charging()` (called from
`hal_loop()` every single iteration whenever the screen is on, no throttling) calls `on_battery()`
-> `PMU.isVbusIn()`, a real I2C round-trip. Every other I2C touch point in this file is
deliberately rate-limited (the 30s battery-percent poll a few lines below it; the 200ms
timer-poll in `deep_idle_loop()` from the 2026-07-20/21 Extreme Power Save work above) - this one
wasn't. With the AXP2101 in a flaky state, each call was taking close to a second even through the
`Wire.setTimeOut(50)` guard (added earlier this same session, see below) - which throttled the
*entire* `hal_loop()`, including `btn_home.loop()`, down to ~1Hz. Button2's click-duration timing
depends on being polled regularly; sampled at ~1Hz it both missed presses landing between samples
and misjudged hold duration on the ones it caught, matching both reported symptoms exactly.

Fix: `on_battery()` now caches the VBUS read for 1s (same cache-and-reuse pattern as the existing
30s poll) instead of hitting I2C on every tick. **Confirmed fixed on-device by the user, both on
USB power and on battery.**

Also landed in the same commit (both already sitting uncommitted in the working tree at the start
of this session):
- `Wire.setTimeOut(50)`, added in `hal_setup()` right before first I2C use. Makes a stuck
  transaction on the shared touch/RTC/PMU bus fail fast instead of blocking indefinitely - doesn't
  fix the root cause above on its own (the loop was still getting throttled to ~1Hz through it),
  but is worth keeping as a backstop against a true indefinite hang.
- `deep_idle_loop()` now re-syncs the clock from the external PCF85063 after an extended
  light-sleep idle stretch, instead of trusting the SoC's internal RTC_SLOW_CLK calibration
  (imprecise RC oscillator, no external crystal wired to it) across however many 200ms cycles it
  just did. User: "initially looking good", not yet soak-tested for a full day.

Committed together as `19a3c3b` on `gremlinDev`.

2026-08-30 (cont.) - added automatic dial screengrab on opening the face-select ("dial selector")
screen, via LVGL's snapshot API
------------------------------------------------------------------------------------------------
`on_watchface_list_open()` (`hal/esp32/app_hal.cpp`) is the existing single hook already called
right when the long-press-on-home dial-selector screen opens - added `save_dial_screengrab()`,
called as its first line, so the outgoing dial gets captured before anything else about that event
runs.

`save_dial_screengrab()` renders `ui_home` (whichever dial is currently in use) off-screen via
`lv_snapshot_take(ui_home, LV_COLOR_FORMAT_RGB565)` - deliberately chosen over reading back the
display driver's own framebuffer, since it renders the object tree directly and so works
correctly even if the caller has already switched the active screen away from `ui_home` by the
time this runs. Required flipping `LV_USE_SNAPSHOT` 0->1 in `include/lv_conf.h` (was compiled out
entirely; a first build after that change silently linked against the old cached, still-disabled
`lv_snapshot.c.o` - PlatformIO's incremental build didn't recompile it off the `lv_conf.h` edit
alone, throwing `undefined reference to lv_snapshot_take` at link time. Fixed with a full
`pio run -e lolin_s3_2_06 -t clean` before rebuilding. Worth remembering if a future `lv_conf.h`
flag flip produces the same link error.

No PNG/JPEG encoder is linked into this build, so the snapshot's raw RGB565 buffer is written out
as an uncompressed 24bpp BMP (hand-rolled ~70-line encoder, no new library dependency) - simplest
format that needs no compression and that any image viewer opens directly once transferred off the
watch. Filename is `/<dial-name>.bmp` (`faces[currentIndex].name`, e.g. `/citizen_410.bmp`), so
`FILE_WRITE`'s truncate-on-open naturally overwrites only that dial's own previous grab rather than
accumulating one file per capture.

Memory footprint: the snapshot buffer for a 240x240 dial is ~115KB, one-shot from
`lv_snapshot_take`'s internal `lv_malloc`, which resolves to plain `malloc()` in this build
(`LV_USE_STDLIB_MALLOC=LV_STDLIB_CLIB` - `LV_MEM_SIZE`'s 144KB build flag governs the *other*,
unused, `LV_STDLIB_BUILTIN` allocator, so it doesn't cap this at all). **Verified from source**
(not just assumed): `hal_setup()` already calls `heap_caps_malloc_extmem_enable(128)` on this board
(see that call's own comment, from the 2026-07-30 wake-from-sleep heap-exhaustion investigation),
which routes any `malloc()` >=128 bytes to the 8MB PSRAM automatically - so this allocation was
never actually at risk from the scarce ~183KB internal heap (which the same boot log shows sitting
at ~92% used even at idle, an already-known, already-accepted baseline from that same investigation
- not something this session's changes affected).

**Real blocker found and fixed**: separately from the memory question, `save_dial_screengrab()`
couldn't have written anything at all on the first flash of this feature - `setupFS()`
(`hal/esp32/app_hal.cpp:839`) returned `false` *before ever calling `FLASH.begin()`* whenever
`ENABLE_CUSTOM_FACE` wasn't defined, which it isn't for `lolin_s3_2_06`. Confirmed live via serial:
boot log read `Setup FS failed` every time. So the filesystem was never mounted at all on this
board's build - not a new regression, a pre-existing gap this feature was the first thing to expose
by actually needing `FLASH` outside the custom-face path. Fixed by always calling `FLASH.begin()`
in `setupFS()` and only gating the `lv_fs_drv`/custom-face registration behind `ENABLE_CUSTOM_FACE`.
Reflashed and confirmed via boot log: `Flash: Total 7118848 => Used 0`, `Drive S is ready` - FFat
now mounts cleanly, ~6.8MB usable (`ffat` partition is 0x6E0000 per `partitions_16M.csv`), so a
~173KB BMP is not remotely a storage-capacity concern.

2026-08-30 (cont.) - dial screengrab: BMP row-padding bug found+fixed, ad hoc serial retrieval
tool built, real dials visually confirmed, "Screengrabber" on/off switch added
------------------------------------------------------------------------------------------------
**Real capture bug found via actual retrieval, not inspection**: the BMP writer computed
`rowBytes = w * 3` with no padding. That happened to work by coincidence for the 240x240 case this
was first written against, but this board's real display is **410x502** (matches the `_410` face
naming convention - `classic_410`, `citizen_410`, `batman_410` are all built for a 410-wide
canvas), and 410*3=1230 isn't a multiple of 4 - BMP rows must be padded to a 4-byte boundary per
spec, and most decoders (PIL included, confirmed) compute that stride themselves from width/bpp
rather than trusting the header's own `biSizeImage`/file-size fields. Every capture from the first
round was silently corrupt - PIL reported `image file is truncated`. Fixed with
`rowBytes = (w*3 + 3) & ~3u`, zero-filled row buffer (`calloc`) so the padding bytes are always 0.

**No download-from-watch path existed, so a minimal one was built** (`handleSerialCommands()`,
wired into `hal_loop()`): a tiny text protocol over the same USB-CDC serial link already used for
flashing - `LIST` enumerates FFat with sizes, `GET:<name>` streams the raw file bytes framed by
`BEGIN:<name>:<size>`/`END:<name>` markers. A `serialDumpActive` flag added to `logCallback()`
suppresses Timber's own `Serial.print` during a GET so log lines can't land mid-stream and corrupt
the byte count - doesn't cover the scattered direct `Serial.print()` calls elsewhere in this file,
fine for a manual, deliberate retrieval with no button presses mid-transfer, not a general fix.
Paired with a local `fetch_screengrabs.py` (pyserial) that lists, downloads, and saves each `.bmp`.
Explicitly a temporary tool for this task, not the "real" transfer mechanism (BLE via the phone
app, most likely) that was already deferred earlier in this same session - revisit if/when that's
asked for.

**Visually confirmed working** after the padding fix: pulled `Classic.bmp`/`Citizen.bmp`/
`Batman.bmp` off the watch, converted to PNG (Pillow), all three loaded correctly at 410x502 and
showed the right dial content (cogs+date+battery / Citizen chronograph replica / Batman face with
subdials+weather). A 4th file (`2151.bmp`, from visiting a 4th/custom face) was also retrieved but
never re-captured post-fix (still the old corrupt version) - user doesn't care about it.

**Added a "Screengrabber" on/off switch**, in the settings screen directly under "Extreme Power
Save" (`ui_screengrabberPanel`/`Switch`/`Label`/`Icon` in `src/ui/ui.c`, cloned from the
`ui_extremePowerSavePanel` block right above it, same `#if ESPS3_2_06` gate, camera icon via the
already-existing `ui_img_camera_png` asset). Backed by `screengrabberEnabled`
(`hal/esp32/app_hal.cpp`), persisted via `prefs` key `"screengrab"`, **defaults to true** (preserves
the already-shipped always-on behavior rather than silently turning the feature off for existing
users). `save_dial_screengrab()` checks the flag first and returns immediately when off, so
disabling it fully removes the capture cost - motivated by the user noticing the dial-selector
open now takes a noticeable ~15s longer with a capture happening (not yet root-caused/measured
which part - `lv_snapshot_take()`'s software render of the whole 410x502 dial tree, or the ~618KB
buffered small-chunk FFat write - is the larger contributor; worth profiling if this needs to get
faster rather than just toggle-off-able).

Flashed and boot-confirmed on real hardware (`Setup FS success`, `Flash: Total 7118848 => Used
2486272` after the 4 stored grabs). The switch's on/off behavior itself (toggling it and confirming

2026-08-31 - Power deep-dive: is sleep as deep as possible, what else can be switched off
(research only, no code changed)
------------------------------------------------------------------------------------------------
User asked for a full audit of Extreme Power Save's current depth and any remaining power-saving
opportunities. Read `hal/esp32/app_hal.cpp`, the CO5300 AMOLED driver
(`.pio/libdeps/lolin_s3_2_06/GFX Library for Arduino/src/display/Arduino_CO5300.cpp`), `pins.h`,
and `platformio.ini` end to end rather than trusting prior notes/memory. Findings below; nothing
in this entry has been implemented yet.

**Confirmed current depth, steps 1-6:**
1. GPIO0 button enabled (`BUTTON_HOME 0`).
2. "Extreme Power Save" Settings switch, persisted.
3. Charge-aware screen timeout (stays on indefinitely on VBUS, button still forces off).
4. Touch chip sleep (`TouchDrvFT6X36::sleep()`/`wakeup()`), I2C polling stops while asleep.
5. BLE fully stopped (`watch.stop(true)`/`watch.begin()`).
6. CPU light sleep, retry #4 (`gpio_wakeup_enable()`/`esp_sleep_enable_gpio_wakeup()`) - confirmed
   working on real battery, committed `33559ac`. The 3s timer safety-net is currently disabled
   (dormant, commented) on suspicion it costs power on its own; that specific timer-off variant
   has only an initial "still works" confirm, not a full soak test.

**Already off / not applicable:** WiFi confirmed unused project-wide (nothing to switch off). No
IMU compiled into this board's build at all (`ENABLE_APP_QMI8658C` undefined for
`lolin_s3_2_06`) - nothing running there to sleep.

**Real, concrete, not-yet-taken win identified: the AMOLED panel itself is never told to sleep.**
Every screen-off call site in `app_hal.cpp` (e.g. line 2882) only calls `screenBrightness(0)`,
which writes the CO5300 driver's brightness register (`CO5300_W_WDBRIGHTNESSVALNOR`) to 0 over
QSPI. It never calls the driver's own `displayOff()` (`Arduino_CO5300.cpp:82`), which sends real
panel `DISPOFF` + `SLPIN` (0x10) commands. At brightness 0 the DDIC's charge pumps/gate
drivers/QSPI receiver logic stay fully powered, driving the panel at zero output - `SLPIN`
genuinely powers those down. Low risk to add (this board's QSPI bus is confirmed
synchronous/blocking, `queue_size=1`, so no reorder risk from two more commands at an already-quiet
point) but adds ~240ms combined latency to sleep/wake transitions
(`CO5300_SLPIN_DELAY`/`CO5300_SLPOUT_DELAY`, 120ms each) - needs a real before/after current-draw
comparison to confirm it's worth that latency, not just assumed from reading the driver. The driver
also exposes an even-deeper, currently-commented-out `CO5300_W_DEEPSTMODE` register in the same
`displayOn()`/`displayOff()` functions - flagged as existing but disabled upstream (possibly
known-unstable there), not recommended to try blind.

**Untapped, lower-priority: `TOUCH_IRQ` (GPIO38) is defined in `pins.h` but never referenced
anywhere in `app_hal.cpp`.** Touch is currently polled via I2C on every LVGL indev tick whenever
the screen is on - not just while trying to sleep - so wiring the real interrupt line would cut
steady-state I2C traffic during ordinary awake use. Smaller and more invasive than the panel-sleep
win above.

**Considered and NOT recommended, three options:**
- CPU frequency scaling while awake-but-idle (`setCpuFrequencyMhz()`, never used anywhere in this
  codebase) - a real lever, but this board runs native USB CDC
  (`ARDUINO_USB_CDC_ON_BOOT=1`) and has already produced one hard-to-recover USB-clock-domain bug
  during the cont. 5/6 light-sleep saga above. Same risk class; only worth trying with the same
  on-battery-only gating discipline already established elsewhere in this file, and real
  on-device testing.
- AXP2101 rail-level power-down of the touch/display supply (cutting the actual voltage rail, not
  just a command-level sleep) - theoretically the deepest possible cut, but blocked the same way
  the RTC-rail question was blocked in the 2026-07-13 entry above: nobody has the Waveshare
  schematic confirming which AXP2101 channel (ALDO/BLDO/DCDC) feeds which peripheral, and guessing
  wrong risks browning out something shared (e.g. the QSPI level shifter). Don't attempt without
  that schematic.
- Real `esp_deep_sleep` instead of light sleep - would cut power further but loses all RAM/LVGL
  state (full reboot + reinit on every wake, real UX cost), and deep sleep's GPIO wake path goes
  through the same ext0/ext1 RTC_PERIPH domain already proven broken on this exact board off USB
  power (see the 2026-08-30 research entry above) - retry #4's whole point was avoiding that
  domain via light-sleep-only GPIO wake, so deep sleep would likely reintroduce the exact failure
  this project already solved.

**Recommended next step, if this is picked up**: implement the CO5300 `displayOff()`/`displayOn()`
change first (highest-confidence, lowest-risk, matches this project's own established
`#if ESPS3_2_06`-gated, one-isolated-change-at-a-time pattern) - build, flash, and confirm on real
hardware, ideally with an actual before/after current measurement rather than just "boots clean" -
before considering the touch-IRQ idea.

**Follow-up, same day: touch-wake investigated, real tradeoff found, not recommended as-is.**
User asked whether the unused `TOUCH_IRQ` line (point above) could let a touch, not just the
button, wake the watch from `deep_idle_loop()`'s light sleep. Read the actual touch driver source
(`SensorLib/src/TouchDrvFT6X36.hpp`) rather than assuming: step 4's existing `sleep()` call writes
`PMODE_DEEP_SLEEP` (`FT6X36_REG_POWER_MODE`), and the driver's own enum comment says that mode
draws ~100uA but **"the reset pin must be pulled down to wake up"** - confirmed by `wakeup()`
itself, which calls `reset()` (a hardware GPIO reset pulse), not an I2C wake command. In this mode
the touch chip's sensing hardware is genuinely powered down; it can't drive `TOUCH_IRQ` on a touch
at all, no matter how `TOUCH_IRQ` itself is wired up in firmware.

Touch-wake would require switching the sleep call from `PMODE_DEEP_SLEEP` to `PMODE_MONITOR`
(same enum, ~3mA per the driver's own comment) instead, then adding `TOUCH_IRQ` (GPIO38) as a
second `gpio_wakeup_enable()` source in `deep_idle_loop()` alongside GPIO0 - mechanically
straightforward, same wake mechanism already proven working for the button. **Not recommended**:
~3mA continuous while "asleep" is a real, likely significant cost against the very ~10x
improvement Extreme Power Save's touch/CPU-sleep steps were measured to deliver - this would be
trading back a meaningful chunk of that saving for wake convenience, not a free win. Button-only
wake stays the deliberately cheaper choice unless the user decides touch-wake convenience is worth
that tradeoff. Nothing implemented; research only.

2026-08-31 (cont.) - Step 7: real CO5300 panel sleep implemented (displayOff()/displayOn()),
built, flashed, boot-confirmed - datasheet numbers pulled for the earlier estimate, real
before/after current measurement still pending
------------------------------------------------------------------------------------------------
Implemented the panel-sleep win identified in the deep-dive entry above. Before writing code,
pulled the real CO5300 datasheet (Waveshare-hosted PDF, this exact chip) rather than guessing
numbers - section 6.2 "DC Characteristics", Stand-by Current table:
- **Sleep In mode** (what `displayOff()` now sends via `DISPOFF`+`SLPIN`): VDDI ~110uA typ (DSI LP
  mode) + VCI ~25uA typ = **~135uA combined typ**.
- **Deep Stand-by mode** (the `CO5300_W_DEEPSTMODE` register the Arduino driver has commented out,
  still unused here): VDDI ~2uA + VCI ~1uA = **~3uA combined typ** - confirms it's a real,
  documented deeper mode, not just an unstable stub, but still not being touched (only exposed via
  a commented-out write in the library, no confidence it's exercised/validated there).
The datasheet's DC Characteristics table has **no explicit "active/on" operating-current figure**
to subtract from - genuinely absent from the document, not an omission on this end - so there's no
datasheet-sourced "before" number to compute an exact delta against. The real saving needs an
actual on-device current measurement; this entry only pins down the "after" (sleep) side precisely.

**Implementation** (`hal/esp32/displays/viewe.hpp`, `hal/esp32/app_hal.cpp`): added
`DisplayWrapper::displayOff()`/`displayOn()` wrappers (`gfx->displayOff()`/`gfx->displayOn()` -
`displayOn`/`displayOff` are plain virtual no-ops on the `Arduino_GFX` base, confirmed by reading
`Arduino_GFX.cpp:3033-3044`, genuinely implemented by `Arduino_CO5300`; every board that includes
`viewe.hpp` constructs a real `Arduino_CO5300`, so this is safe for all of them, not just
`ESPS3_2_06`). New `displayAsleep` flag in `app_hal.cpp`, same pattern as `touchAsleep`/`bleAsleep`.
**Deliberately gated inside the same `extremePowerSave && on_battery()` block as touch
sleep/BLE stop (step 4/5's own gate)**, not on every plain screen timeout - the call sends real
`DISPOFF`+`SLPIN`, adding ~240ms combined blocking delay on wake
(`CO5300_SLPIN_DELAY`/`CO5300_SLPOUT_DELAY`, 120ms each via `displayOn()`'s `DISPON`+`SLPOUT`
sequence). That cost is only acceptable stacked onto the already-slower GPIO/button wake path
(`deep_idle_loop()` -> `screen_on()`), which already pays touch's own ~200ms reset cost - not on an
ordinary touch-driven wake, which needs to feel instant and never sets this flag. `screen_on()`
wakes the panel first (before touch/BLE), so `deep_idle_loop()`'s existing "immediate backlight"
fix (2026-07-20/21 cont. 7, fix #3) now also waits out this ~240ms before the backlight becomes
visible on a button press - a real, known latency regression on that specific path, flagged here
so it isn't mistaken for a new bug if noticed during soak testing.

Built clean (`pio run -e lolin_s3_2_06`): RAM 45.4%, Flash 85.4% - both unchanged from the
pre-change build, confirming this added negligible code size. Flashed via the safe method
(`pio run -e lolin_s3_2_06 -t upload`, real 3-segment write, NVS/settings preserved). Boot log
captured via a DTR/RTS reset pulse - clean: `Setup FS success`, `AXP2101 battery: 100%, charging:
0, vbus: 1`, `Setup done`, BLE `[DEBUG]: Connected`. No crash, no regression visible at boot.

**Not yet soak-tested for the actual power delta or the button-wake latency feel.** Next step:

comparing current draw during an idle `deep_idle_loop()` stretch before vs. after this change (or
simply confirming overall battery life improves further from the already-measured ~10x baseline),
